## 1. 产品概述

Coffer 是一款个人凭证管理器，用于安全保存账号密码、卡片证件与安全笔记，支持 Web、桌面、移动三端，同一套数据模型与加密逻辑。

**一句话定位**：只记一个秘密（主密码），其余全部安全托管。

**产品原则：一切从简。** v1 刻意收窄范围，砍掉一切非必需能力（见 §9「不做」），把加密安全这个核心做扎实。

## 2. 总体架构与安全口径

### 2.1 零知识模型（核心原则）

| 口径 | 说明 |
|---|---|
| 云端只存密文 | 所有敏感内容（条目名称、用户名/密码/卡号/正文/附件、文件夹名）由**客户端加密后上传**，云端不含明文、不含密钥 |
| 服务端不可反推主密码 | 登录认证采用 SRP 类协议，服务端只保存盐与验证器 |
| 搜索/筛选在客户端完成 | 收藏、类型筛选、关键词匹配均为客户端解密后在内存完成；v1 不做服务端加密索引 |
| 忘记主密码 = 数据不可恢复 | 无找回机制，注册与修改主密码时均需明示确认 |

### 2.2 单一主密码（已定决策）

- **登录 = 解锁**，不设双密码分离。理由：只记一个秘密，符合"一切从简"。
- **修改主密码 = 全库重加密**：客户端用新密钥重加密全部条目与附件后上传，`key_version` 递增；历史密文云端不留存。
- 查看单条详情需**再次验证**（仅主密码，已移除生物识别）。

### 2.3 存储口径

- 数据**只存云端**（客户端加密后上传），**不做本地离线副本**；退出登录不会删除任何云端数据。
- 图片附件：客户端加密后上传至对象存储，云端只存密文文件。

> 密钥派生、加密格式、SRP 认证的算法选型、计算方法与完整工作流程见 **附录 A**。

## 3. 账户体系

### 3.1 注册

- 必填：邮箱 + 主密码 + 二次确认主密码
- 密码强度提示：< 8 位红 / 中等橙 / 强绿（至少 8 位，建议 12 位以上）
- 必须勾选「我了解：主密码是唯一的解锁凭证，服务端无法找回，遗失将永久无法访问本保险库」后才允许创建

### 3.2 登录 / 退出

- 邮箱 + 主密码登录；演示环境任意输入可通过（原型）
- 退出登录：清空本地会话态（选中条目、解锁状态、搜索与筛选、表单内容），返回登录页；云端密文数据不受影响
- 原型中有「上次同步」字样为遗留文案，待清理（见 §10 待定项）

### 3.3 个人资料

| 字段 | 可否修改 | 说明 |
|---|---|---|
| 头像 | 可修改 | 上传图片（客户端加密后上传），≤3MB；删除后回落为文字头像 |
| 文字头像 | 自动 | 未上传头像时显示昵称前两个字符 + 用户自选底色（9 色色板） |
| 昵称 | 可修改 | 16 字以内，非空校验 |
| 邮箱 | 不可修改 | 登录标识，只读展示 |

## 4. 凭证管理（核心功能）

### 4.1 类型 = 主体表单（已定决策）

类型决定条目使用哪张表单，云端不感知类型含义：

| 类型 | 表单字段 |
|---|---|
| 账号 | 用户名、密码、网址 |
| 卡片证件 | 卡号、证件号、有效期、密码 PIN（可选） |
| 安全笔记 | 正文 |

### 4.2 图片是附件，不是类型（已定决策）

- 任何条目都可挂图片附件（账号挂实名单截图、卡片挂正反面等）
- 仅支持从相册/本地选择，**不支持拍照**
- 单文件 ≤ 3MB

### 4.3 新建 / 编辑

- 新建时顶部三段切换选择类型，切换类型后非共用字段不残留
- **编辑时类型锁定**：当前类型高亮、其余两项变淡且不可点击（悬浮提示"类型创建后不可更改"）；换类型场景走"新建"
- 顶栏布局（移动端）：取消 居左 / 标题 居中 / 保存 居右
- 图片附件区：账号/卡片/笔记均可添加、预览（全屏查看器）、删除

### 4.4 列表与视图

- **左栏只有两组**（PC）：保险库（全部凭证 / 收藏）、文件夹——类型不作为导航项
- **类型筛选的唯一入口**是列表上方的筛选胶囊（全部/账号/卡片/笔记），只做子筛选、不改变"所在位置"
- 导航高亮规则：左栏同一时刻只高亮一个"位置"；在文件夹/收藏内用筛选条时左栏保持原位，标题显示组合状态（如「个人 · 卡片证件」）
- 搜索范围：名称 / 用户名 / 卡号 / 备注（客户端解密匹配）
- 列表行：文字头像或类型标识 + 名称 + 副标题（用户名 / 卡号尾号脱敏 / "安全笔记"）；已收藏条目显示星标
- 卡号在列表中脱敏显示尾号

### 4.5 收藏

- 列表行星标 + 详情页星形按钮（PC）双向联动
- 收藏计数实时增减；在收藏视图取消收藏，条目离场并自动选中下一条
- 收藏属于元信息，锁定态也可操作

### 4.6 文件夹

- 新建 / 重命名 / 删除；9 色色板自定义颜色
- 删除文件夹时，其下条目自动移入「未分类」（`folder_id` 置 NULL）
- 文件夹只是分类，不参与加密

### 4.7 详情与二次验证（已定决策）

- 进入详情默认**锁定**：只显示标题、类型、文件夹、修改时间等元信息，正文区显示锁形说明 + 解锁按钮 + 骨架占位
- 解锁仅输入主密码（生物识别已移除）；解锁仅对当前条目有效，切换/返回再进重新上锁
- 锁定态不渲染复制按钮与图片区块；编辑按钮先验证再打开表单
- 新建保存后自动免验证一次（刚录入的内容无需立刻再验）
- 详情信息分层：标题区（名称/类型/文件夹/收藏/操作）→ 字段区 → 图片附件区 → 时间戳（创建/最近修改），无重复信息

### 4.8 复制与删除

- 复制密码/PIN：10 秒后自动清空剪贴板
- 删除：二次确认 → 移入回收站（`del_flag=2`），保留 30 天后物理清除（含附件密文文件）；条目名称长按删除（移动端）

### 4.9 修改主密码

- 入口：移动端「我的 → 修改主密码」；PC「个人资料 → 安全 → 修改主密码」
- 表单：当前密码 + 新密码 + 二次确认；校验链：非空 → ≥8 位 → 两次一致 → 不与旧密码相同
- 成功后全库重加密（`key_version` 递增），其他设备需重新登录

## 7. 数据库概要（详见 `docs/sql/coffer-v1.sql`）

| 表 | 职责 | 关键字段 |
|---|---|---|
| sys_user | 用户 + 认证 | email（唯一）、SRP 盐/验证器、key_version、头像/底色 |
| vault_folder | 文件夹 | folder_name_cipher、color、sort_no |
| vault_item | 凭证条目 | item_type（0/1/2）、name_cipher、data_cipher（整体 JSON 密文）、fav_flag、folder_id（NULL=未分类）、deleted_time |
| vault_attachment | 图片附件 | object_key（密文文件）、mime、file_sha256 |

所有表统一携带基础字段：`status`（0正常 1停用）、`del_flag`（0存在 2删除）、`create_by` / `create_time` / `update_by` / `update_time` / `remark`。不建物理外键，逻辑关系由应用层维护。

**关键流转**：
- 删除条目 → `del_flag=2` + 记 `deleted_time`，定时任务清理超 30 天记录及对象存储文件
- 修改主密码 → `sys_user.key_version` +1，全量条目/附件重加密更新

## 附录 A · 加密设计详述

> 本附录是 §2 安全口径的实现规范：密钥怎么来、数据怎么加密、登录怎么验证、以及端到端工作流。开发实现以本附录为准。

### A.1 密钥派生（KEK 的来历）

主密码不能直接当密钥用（强度不够、且需要"算得慢"来抵抗爆破），先做密钥派生：

```
主密码
   │
   ▼
Argon2id（内存 64MB / 迭代 3 / 并行 2；备选 PBKDF2-SHA256 × 600,000）
   │   输入：主密码 + Salt_Enc（客户端随机生成，存 sys_user.enc_salt）
   ▼
256 位数据加密密钥 KEK（Data Encryption Key）
```

设计要点：

- **故意慢**：用户登录时多花几百毫秒无感，但攻击者字典爆破时每个候选都要付同样的时间成本，暴力破解成本放大数十万倍
- **Salt_Enc 每用户随机**：相同主密码在不同账户下派生出完全不同的密钥，预计算彩虹表全部失效
- **KEK 只存在于客户端内存**，不上传、不落盘；登录/解锁时由主密码现场重派生

### A.2 数据加密格式（AES-256-GCM）

所有 `_cipher` 字段使用同一套格式：

```
cipher = "v1." + Base64( Nonce(12B) ‖ Ciphertext ‖ Tag(16B) )
            ↑算法版本    ↑随机数      ↑密文      ↑认证标签
```

- **Nonce 每次加密随机生成、绝不复用**：同一条内容改一个字母再保存，密文完全不同，云端无法比对"哪里改了"
- **GCM 自带完整性校验（Tag）**：密文被篡改任何一个 bit，客户端解密时直接报错拒绝，不会解出错误数据
- **`v1.` 版本前缀**：将来更换算法（如后量子）时按前缀兼容解密旧数据

**字段级应用（对应 `docs/sql/coffer-v1.sql`）**：

| 字段 | 加密内容 |
|---|---|
| `vault_item.name_cipher` | 条目名称（列表标题） |
| `vault_item.data_cipher` | 整条内容 JSON（账号=用户名/密码/网址；卡片=卡号/证件号/有效期/PIN；笔记=正文）整体加密，服务端无字段级明文 |
| `vault_folder.folder_name_cipher` | 文件夹名 |
| `vault_attachment.file_name_cipher` | 附件原始文件名 |
| `vault_attachment.object_key` 指向的文件 | 图片文件整体字节流加密后上传对象存储 |

**明文元信息及理由**（服务器可见但不含内容）：

| 字段 | 为什么可以明文 |
|---|---|
| `item_type`（0/1/2） | 仅用于类型筛选；隐藏它需全量拉回客户端筛选，v1 不做 |
| `fav_flag`、`folder_color` | 收藏状态、UI 颜色 |
| `mime_type`、`file_size` | 文件格式与大小 |
| `email` | 登录标识 |
| `status` / `del_flag` / 时间戳 | 状态与审计 |

> 待定项：`nickname` 当前明文（服务端展示便利）；如需严格零知识改为 `nickname_cipher`，代价是昵称只能由客户端渲染。

### A.3 登录认证：SRP（auth_salt + auth_verifier）

目标：向服务器证明"我知道主密码"，但**主密码与它的哈希都不上网络、不进服务器**。

#### A.3.1 注册（一次性）

```
客户端：
1. 随机生成 16 字节盐 s                        → auth_salt
2. x  = H(s, 邮箱, 主密码)                     ← 慢哈希派生
3. 验证器 v = g^x mod N                        ← 2048 位群，单向，无法由 v 反推 x
上传 email + s + v → 存 auth_salt / auth_verifier
本地丢弃：主密码、x、v
```

#### A.3.2 登录（每次）

公开参数：大素数 N、生成元 g、常数 k = H(N, g)。

```
① 客户端 → 服务器：邮箱
② 服务器 → 客户端：盐 s + 临时随机数 B = k·v + g^b     （b 为服务器随机数）
③ 客户端（本地）：
     由主密码 + s 重算 x（盐相同 → x 与注册时一致）
     随机数 a，公开值 A = g^a
     会话密钥 S = (B − k·v)^(a + u·x)                  （u = H(A,B)）
     证明码   M1 = H(A, B, S)
④ 客户端 → 服务器：A + M1
⑤ 服务器（本地验证）：
     S' = (A · v^u)^b
     M1' = H(A, B, S')
     M1 === M1' ？ → 通过登录 ： → 拒绝
```

**⑤ 为什么能成立（殊途同归的数学）**：模幂可换序 `(g^a)^b = (g^b)^a = g^(ab)`。

```
客户端路径：B − k·v = g^b（它知道 x，能自己算出 v 并从 B 中剥出 g^b）
            S = (g^b)^(a+u·x) = g^(ab + u·x·b)

服务器路径：A · v^u = g^a · (g^x)^u = g^(a + u·x)
            S' = (g^(a+u·x))^b = g^(ab + u·x·b)
```

两条路径落点相同：`S = S' = g^(ab + u·x·b)`，同时含 a、b、x 三者的贡献——x 只能来自主密码，所以对上暗号即证明"对方知道主密码"。M1 是对 S 的哈希承诺：S 从不上网络，服务器只是用自己算的 S' 哈希后与客户端报的答案比对。

**安全性质**：

| 威胁 | 防护 |
|---|---|
| 网络抓包 | 传输的只有 A、B、M1 等随机数与证明码，无密码、无密码哈希 |
| 服务器被拖库 | 只剩 s、v；v = g^x 单向，无法反推 x，也无法离线测试候选密码（这是选 SRP 而非"传密码哈希"的根本原因） |
| 重放攻击 | A、B 每次登录随机，旧流量重放无效 |
| 中间人 | M1/M2 双向证明绑定会话参数 |

#### A.3.3 双盐分离（为什么有两个盐）

| | auth_salt（SRP 用） | enc_salt（KDF 用，派生 KEK） |
|---|---|---|
| 派生目标 | 登录验证材料 x | 数据加密密钥 |
| 为何必须分开 | SRP 要求服务器长期保存 verifier；若登录与加密共用一条派生链，等于把"主密码可算出的量"交给服务器，为离线爆破开口子 | 两套独立派生链，互不泄露 |

### A.4 端到端工作流

**① 注册**：校验密码强度 → 勾选"无法找回" → 客户端生成 auth_salt / enc_salt → 计算 v 上传 → `INSERT sys_user`（key_version=1）。

**② 登录 / 解锁**：SRP 五步握手（A.3.2）→ 成功后客户端用主密码 + enc_salt 现场重派生 KEK（密钥只在内存，不落盘）。

**③ 新建凭证**：客户端组装明文 JSON → KEK + 随机 Nonce 做 AES-256-GCM → `INSERT vault_item (name_cipher, data_cipher, key_version=1)`；图片附件同样处理后传对象存储，`INSERT vault_attachment`。

**④ 列表 / 搜索 / 筛选**：`SELECT … WHERE user_id=? AND del_flag='0'` 拉回密文 → 客户端逐条解密到内存 → 渲染标题、执行关键词匹配与类型/收藏筛选 → 服务器全程不知内容与搜索词。

**⑤ 查看详情（二次验证）**：重新输入主密码 → 派生 KEK 解密该条 data_cipher → 仅本条解锁；切换条目重新上锁。

**⑥ 修改主密码（全库重加密）**：本地验证旧密码 → 旧 KEK 解密全部条目/附件 → 新密码派生新 KEK → 逐条重加密上传 → `sys_user.key_version`+1，各条 key_version 同步刷新；服务器只见新旧两批密文。期间建议锁定其他设备写入（见 §11-3）。

**⑦ 忘记主密码**：无任何找回路径——KEK 只由主密码派生，主密码丢失后云端密文永久不可解，这是产品必须向用户明示的代价。

### A.5 算法与参数基线

| 项 | 基线 | 备选 |
|---|---|---|
| 密钥派生 | Argon2id（64MB / t=3 / p=2） | PBKDF2-SHA256 × 600,000 |
| 数据加密 | AES-256-GCM，Nonce 12B 随机 | ChaCha20-Poly1305 |
| 登录认证 | SRP-6a，2048 位群 | OPAQUE |
| 密文格式 | `v1.` + Base64(Nonce‖C‖Tag) | 版本前缀兼容演进 |
| Salt 长度 | auth_salt / enc_salt 均 16 字节随机（Hex 32 字符） | — |

### A.6 内容解密流程

解密是 A.2 加密的逆过程，核心动作只有 AES-256-GCM 解密一步，但它嵌在从"打开页面"到"看到标题"的完整链路里。本节约定客户端的标准解密流程与失败分支处理。

#### A.6.1 前置条件：内存中的 KEK

任何解密发生之前，客户端必须持有 KEK。KEK 不从服务器获取，而是登录/解锁成功后现场派生：

```
SRP 登录成功
   → 主密码（仅存在于客户端内存）
   → 服务器下发 enc_salt
   → Argon2id( 主密码, enc_salt ) = KEK
   → KEK 保存在内存变量中，不落盘、不上传，会话内所有解密复用
```

- **锁定功能的本质**：清空内存中的 KEK。密文仍在云端，但无钥可解；解锁 = 重输主密码重派生 KEK
- KEK 派生只发生在登录、解锁、详情二次验证三个时机，日常浏览列表不重复派生

#### A.6.2 标准流程（以列表页为例）

**① 拉取密文**：`SELECT id, item_type, fav_flag, folder_id, name_cipher, data_cipher, key_version FROM vault_item WHERE user_id=? AND del_flag='0'`。服务器筛选用明文元信息（item_type / fav_flag），**不参与任何内容搜索**——关键词匹配由客户端解密后在内存完成。

**② 拆包**（A.2 格式的逆操作）：

```
"v1." + Base64( Nonce(12B) ‖ Ciphertext ‖ Tag(16B) )
  │                │
  │                └─ 解 Base64 → 得到 Nonce / Ciphertext / Tag 三段二进制
  └─ 版本前缀决定算法（v1. → AES-256-GCM；将来 v2. → 新算法）
```

**③ GCM 解密 + 验签（一体）**：

```
AES-256-GCM-Decrypt( key = KEK, nonce, ciphertext, tag )
  ├─ Tag 校验通过 → 输出明文字节
  └─ Tag 校验失败 → 抛错终止，绝不输出部分明文
```

GCM 的认证标签把"解密"与"验完整性"绑定：密文被篡改哪怕 1 bit，Tag 校验必然失败，客户端报错拒绝而非解出乱码继续执行。因此**解密失败只可能意味着"密钥不对"或"数据被动过"**，二选一，见 A.6.3 分支表。

**④ 还原业务数据**：明文字节即当初加密前的 JSON，`JSON.parse` 后渲染。列表页对每条密文重复 ②③④，全部完成后一次性渲染（避免逐条显示）。图片附件同理：OSS 下载密文文件 → 拆包 → GCM 解密 → 原始图片字节喂给 `<img>`，全程内存内。

#### A.6.3 失败分支约定

| 现象 | 含义 | 客户端处理 |
|---|---|---|
| **全部条目解不开** | KEK 不对（换设备、会话 KEK 过期等） | 引导重新解锁 / 重新登录 |
| **个别条目解不开，其余正常** | 该条 Tag 校验失败：数据被篡改或损坏 | 单条标红"数据校验失败"，不影响其他条目 |
| **key_version 不匹配** | 改主密码未完成：该条仍是旧版本密文，KEK 已为新版本 | 用旧密钥补解，或提示"同步未完成，稍后重试" |

`key_version` 的存在即为此服务：每条密文自报加密版本，客户端与 KEK 版本比对后走对应分支。

#### A.6.4 流程总览

```
主密码 + enc_salt ──Argon2id──▶ KEK（内存）
                                   │
密文行（服务器）──HTTPS──▶ 拆格式 ─┴─▶ GCM 解密 + 验 Tag ──▶ JSON ──▶ 界面
                                        │
                                        └─ 失败 → 报错 / 重新解锁，绝不输出部分明文
```

与加密对照：加密是 `JSON → GCM 加密 → v1. 格式 → 上传`，解密是 `拉取 → 拆格式 → GCM 解密 → JSON`，钥匙始终是只在客户端内存中的 KEK。
